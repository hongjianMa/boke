# 需求工程

## 需求分析的主要任务是什么？

需求分析的主要任务是明确软件系统要做什么。具体包括获取和分析用户需求，确定系统的功能需求、性能需求、接口需求和约束条件，建立需求模型，并编写软件需求规格说明书，最后对需求的正确性、完整性、一致性和可验证性进行确认，为后续软件设计、开发和测试提供依据。

| 需求类型 | 主要内容                         |
| -------- | -------------------------------- |
| 功能需求 | 系统要完成哪些功能               |
| 性能需求 | 响应时间、并发量、准确率等       |
| 接口需求 | 用户接口、系统接口、软硬件接口   |
| 约束条件 | 技术、标准、安全、开发环境等限制 |

## 功能需求和非功能需求有什么区别？

- 功能需求：系统需要完成什么功能，例如用户登录、订单查询。
- 非功能需求：系统需要达到什么质量要求，例如响应时间、安全性、可靠性、并发能力。

## 可行性分析

通常包括：

技术可行性；
经济可行性；
操作可行性；
法律可行性；
时间可行性。

## 如何判断一个需求是否合理？

判断一个需求是否合理，主要看它是否必要、正确、明确、完整、一致、可行和可验证。首先要确认它是否能够解决真实的用户或业务问题；其次要评估技术、成本和时间上是否可实现；同时检查需求是否存在歧义、是否与其他需求冲突，以及能否制定明确的测试和验收标准。一个合理的需求应当有明确来源、能够实现并且可以验证。

## 需求发生变化怎么办？

需求发生变化时，应当通过规范的变更管理流程处理。首先记录变更内容和原因，然后分析它对系统设计、代码、测试、进度和成本的影响；经过相关人员评审批准后，再更新需求和设计文档，实施修改并进行回归测试和验收。这样可以避免需求被随意修改，保证项目范围、进度和质量处于可控状态。

## SRS（Software Requirements Specification，软件需求规格说明书）

是用于准确描述软件系统“要做什么”，是设计、开发、测试和验收的重要依据。

一份高质量的 SRS 通常应具备以下特点：

| 特点         | 含义                                         |
| ------------ | -------------------------------------------- |
| **正确性**   | 准确反映用户的真实需求                       |
| **完整性**   | 功能、性能、接口、异常情况等描述完整         |
| **一致性**   | 各项需求之间不存在矛盾和冲突                 |
| **无歧义性** | 每项需求只有一种明确的解释                   |
| **可行性**   | 在技术、成本和时间条件下能够实现             |
| **可验证性** | 能够通过测试或验收判断是否满足               |
| **可修改性** | 文档结构清晰，需求变化时便于修改             |
| **可追踪性** | 能追踪需求的来源，以及对应的设计、代码和测试 |
| **有优先级** | 能区分需求的重要程度和实施顺序               |

> 一份良好的 SRS 应当具有正确性、完整性、一致性、无歧义性、可行性和可验证性，同时还应便于修改和追踪。也就是说，需求要准确反映用户需要，内容完整且不冲突，描述清楚，能够实现，并且能够通过测试或验收进行确认。


## 用例图有什么作用?

用例图（Use Case Diagram）**是 UML 中用于描述系统功能需求的图，主要展示：

谁使用系统、系统提供什么功能，以及用户与功能之间的关系。

用例图是 UML 中描述系统功能需求的一种图，主要表示参与者、系统用例以及它们之间的关系。它可以从用户角度说明系统提供哪些功能，明确不同参与者的权限和系统边界，帮助用户与开发人员沟通需求，并为后续系统设计、测试和验收提供依据。
