# 事务
所谓事务是用户定义的一个数据库操作序列，这些操作要么全做，要么全不做，是一个不可分割的工作单位。

## 事务的ACID特性
- 原子性(Atomicity)：指事务中包括的操作要么都做，要么都不做
- 一致性(consisttency)：是指事务执行的结果必须是使数据库从一个一致性状态转为另一个一致性状态。
> 前后保持状态一致
- 隔离性(isolation)：是指一个事务的执行不能被其他事务干扰
> 事务间不相互干扰
- 持续性(durability)：也叫永久性，是指一个事务一旦提交，他对数据库中的数据的改变就是永久的。

# 并发控制
事务是并发控制的基本单位。
## 并发一致性问题
- **丢失修改**：两个事务T1和T2读入同一数据，各自进行修改,T2提交的结果破坏了T1提交的结果，导致T1的修改被丢失。
- **脏读**：指事务T1修改某一数据并写回磁盘，事务T2读取同一数据后，T1由于某种原因被撤销，这时被T1修改过的数据恢复原值，T2读到的数据就与数据库中的数据不一致，则T2读到的数据就是脏数据。
- **不可重复读**：是指事务T1读取数据之后，事务T2执行更新操作，当事务T1再次读取该数据时，得到与前一次不同的值。
- **幻读**：指事务T1读取数据后，事务T2执行插入或删除操作，使T1无法再现前一次读取结果。

# 封锁

## 基本锁：S 锁与 X 锁

### ① S 锁：共享锁，也叫读锁

事务对数据 A 加 **S 锁**之后：

- 自己可以读 A。
- 不能修改 A。
- 其他事务也可以给 A 加 S 锁。
- 其他事务不能给 A 加 X 锁。

所以可以理解为：

> **读和读可以同时进行。**

------

### ② X 锁：排他锁，也叫写锁

事务对数据 A 加 **X 锁**之后：

- 可以读取 A。
- 可以修改 A。
- 其他事务不能再对这个数据加 S 锁或 X 锁。

可以理解为：

> **只要有人在写，别人既不能读锁，也不能写锁。**

最基本的兼容关系：

| 已经加的锁 | 再加 S | 再加 X |
| ---------- | ------ | ------ |
| S          | ✅      | ❌      |
| X          | ❌      | ❌      |



------

## 三级封锁协议

三级封锁协议主要解决三个问题：

> **丢失修改 → 读脏数据 → 不可重复读**

可以递进记忆。

------

### 一级封锁协议

规定：

> **修改数据前必须加 X 锁，并且直到事务结束才释放。**

即：

```
修改 A
↓
加 X(A)
↓
一直持有
↓
COMMIT / ROLLBACK
↓
释放
```

解决：

> **丢失修改。**

例如两个事务同时修改余额，因为 X 锁互斥，就不会相互覆盖修改结果。

------

### 二级封锁协议

在一级基础上增加：

> **读取数据前必须加 S 锁，但读完可以立即释放 S 锁。**

即：

```
读：
S → 读取 → 释放


写：
X → 修改 → 事务结束 → 释放
```

解决：

- ✅ 丢失修改。
- ✅ 读脏数据。

为什么能防脏读？

事务 A 修改数据后有 X 锁且尚未提交：

```
A：X(A)
```

事务 B 想读取：

```
B：申请 S(A)
```

由于：

```
S 和 X 不兼容
```

所以 B 必须等 A 提交或回滚后才能读取。

但二级协议仍可能：

> **不可重复读。**

因为读完以后 S 锁马上释放，别人可以修改。

------

### 三级封锁协议

在二级基础上进一步规定：

> **读取数据时加 S 锁，并且 S 锁也要一直持有到事务结束。**

也就是：

```
读：
S → 读取 → …… → COMMIT → 释放


写：
X → 修改 → …… → COMMIT → 释放
```

因此可以解决：

- ✅ 丢失修改。
- ✅ 读脏数据。
- ✅ 不可重复读。

为什么防止不可重复读？

事务 A 第一次读取：

```
A：S(A)
```

并且一直不释放。

此时事务 B 想：

```
X(A)
```

由于：

```
S 与 X 不兼容
```

B 必须等事务 A 结束。

所以事务 A 在整个事务期间再次读取 A，都不会被别人修改。

------

### 三级封锁协议总结表

这张表很适合直接背：

| 协议 | X 锁                   | S 锁                 | 解决问题     |
| ---- | ---------------------- | -------------------- | ------------ |
| 一级 | 修改前加，事务结束释放 | 无特殊要求           | 丢失修改     |
| 二级 | 修改前加，事务结束释放 | 读前加，读完释放     | + 脏读       |
| 三级 | 修改前加，事务结束释放 | 读前加，事务结束释放 | + 不可重复读 |

口诀：

> **一级锁写，二级锁读，三级读锁也不提前放。**

或者按解决问题记：

> **一级防丢失，二级防脏读，三级防重复。**

------

## 两段锁协议 2PL

一个事务的加锁和解锁必须分成两个阶段：前半段只能加锁，后半段只能解锁

### 第一阶段：生长阶段

只能：

> **申请锁、增加锁。**

不能释放锁。

```
加 S
加 X
加锁
加锁
……
```

------

### 第二阶段：缩减阶段

只能：

> **释放锁。**

一旦开始释放锁：

> **就不能再申请新的锁。**

因此：

```
生长阶段             缩减阶段


加锁 → 加锁 → 加锁 | 解锁 → 解锁 → 解锁
                  ↑
                分界点
```

不能出现：

```
加锁 → 解锁 → 又加锁
```

这违反两段锁协议。

## 严格两段锁协议和强两段锁协议

**两段锁协议（2PL）的两个加强版本：严格两段锁协议和强两段锁协议**。

先以普通两段锁协议为基础理解：

> 普通 2PL：**先加锁，后解锁；一旦开始解锁，就不能再申请新锁。**

### 1. 严格两段锁协议（Strict 2PL）

在普通 2PL 基础上增加一条要求：

> **所有 X 锁（写锁）必须一直保持到事务 COMMIT 或 ROLLBACK 才能释放。**

例如：

```
加 S(A)
加 X(B)
读取 A
修改 B
释放 S(A)
……
COMMIT
释放 X(B)
```

这里 S 锁可以提前释放，但 **X 锁不能提前释放**。

这样做的主要好处是：

- 防止其他事务读取或修改尚未提交的数据。
- 避免**脏读**。
- 避免**级联回滚**。

可以记成：

> **严格 2PL：写锁必须撑到事务结束。**

------

### 2. 强两段锁协议（Rigorous 2PL）

比严格 2PL 更严格：

> **所有锁，不管 S 锁还是 X 锁，都必须保持到 COMMIT 或 ROLLBACK 才能释放。**

例如：

```
加 S(A)
加 X(B)
读取 A
修改 B
……
COMMIT
↓
释放 S(A)
释放 X(B)
```

事务执行过程中**一个锁都不提前释放**。

记成：

> **强 2PL：读锁、写锁全部撑到事务结束。**

------

### 3. 三者对比

| 协议         | S 锁何时释放         | X 锁何时释放         |
| ------------ | -------------------- | -------------------- |
| 普通 2PL     | 进入缩减阶段后可释放 | 进入缩减阶段后可释放 |
| **严格 2PL** | 可以提前释放         | **事务结束才释放**   |
| **强 2PL**   | **事务结束才释放**   | **事务结束才释放**   |

关系可以理解为：

**强两段锁协议 ⇒ 严格两段锁协议 ⇒ 普通两段锁协议。**

考试时最简单的记忆方式就是：

> **普通：先加后解；严格：X 不早退；强：S、X 都不早退。**
