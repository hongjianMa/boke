## 数据库设计的基本流程

数据库设计一般分为 6 个阶段：

1. 需求分析
   - 分析用户需要什么数据、什么功能，以及性能要求。
2. 概念结构设计
   - 用 **E-R 模型**描述现实世界。
   - 主要产物是 **E-R 图**。
3. 逻辑结构设计
   - 把 E-R 图转换成关系模型，也就是转换成一张张关系表。
4. 物理结构设计
   - 决定数据在磁盘上怎么存。
   - 包括存储结构、索引、存取路径等。
5. 数据库实施
   - 建表、编写程序、导入数据、测试、试运行。
6. 运行和维护
   - 数据库正式投入使用后的维护、优化、备份等。

可以简单记成：

> **需求 → E-R 图 → 关系表 → 怎么存 → 实现 → 维护。**

------

# 主键和外键

## 1. 主键 Primary Key

作用：

> **唯一标识表中的一条记录。**

特点：

- 不能重复。
- 不能为 NULL。
- 一张表只能有一个主键。
- 主键可以由一个属性组成，也可以是多个属性组成的联合主键。

例如学生表：

```
Sno | Sname | Sdept
```

如果 Sno 是学号，那么：

```
Sno → 唯一确定一个学生
```

因此 Sno 可以作为主键。

------

## 2. 外键 Foreign Key

作用：

> **建立两张表之间的联系。**

例如：

```
学生表
Sno, Sname


选课表
Sno, Cno, Grade
```

选课表中的 `Sno` 引用学生表的主键 `Sno`，因此它是外键。

- 可以重复。
- 可以为 NULL，具体要看约束定义。
- 一张表可以有多个外键。

# 函数依赖

这是后面范式的基础，也是这一部分最关键的概念之一。

## 什么叫函数依赖

记：

A→B

表示：

> **A 能唯一确定 B。**

也可以说：

> **B 函数依赖于 A。**

例如：

```
学号 → 姓名
```

因为知道一个学生的学号，就能够唯一确定他的姓名。

再比如：

```
身份证号 → 姓名
```

也属于函数依赖。

------

# 键码、候选键的思想

假设：

{A1,A2,…,An}

能够函数确定关系中的**全部属性**，并且这个属性集合已经是最小的，那么它可以作为一个**候选键**。

简单理解：

> **能够唯一确定整行数据，而且再少一个属性就不行。**

例如选课关系：

```
Sno, Sname, Sdept, Mname, Cname, Grade
```

如果一个学生可以选多门课程，那么单独的：

```
Sno
```

不能确定成绩。

单独的：

```
Cname
```

也不能确定成绩。

但：

```
(Sno, Cname)
```

可以唯一确定一条选课记录。

所以可能有：

(Sno,Cname)→(Sname,Sdept,Mname,Cname,Grade)

因此 `(Sno, Cname)` 可以作为候选键。

------

# 完全函数依赖和部分函数依赖

这个知识点主要用于理解 **2NF**。

假设：

A→B

## 完全函数依赖

如果 A 中任何一部分都无法单独确定 B，那么：

> B **完全函数依赖**于 A。

例如：

(Sno,Cno)→Grade

通常：

```
Sno → Grade   ×
Cno → Grade   ×
```

必须同时知道学生和课程才能确定成绩，因此：

(Sno,Cno)完全Grade

------

## 部分函数依赖

如果 A 是一个组合属性，但其中一部分就已经能够确定 B，则称：

> B **部分函数依赖**于 A。

例如：

(Sno,Cno)→Sname

但实际上：

Sno→Sname

只需要 Sno 就够了，因此 Sname 对 `(Sno,Cno)` 是**部分函数依赖**。

这正是 2NF 要解决的问题。

------

# 传递函数依赖

如果：

A→B

并且：

B→C

于是：

A→C

如果 A 不是直接决定 C，而是通过 B 间接决定 C，就叫：

> **传递函数依赖。**

例如：

```
学号 → 学院
学院 → 院长
```

所以：

```
学号 → 院长
```

这里院长对学号存在传递依赖。

这是 **3NF** 重点解决的问题。



------

# 范式

范式可以理解为：

> **对关系表设计质量的一系列等级要求。**

基本递进关系是：

BCNF⇒3NF⇒2NF⇒1NF

也就是说：

> 范式等级越高，约束越严格。

------

## 第一范式 1NF

核心：

> **属性不可再分，每个单元格只能存一个原子值。**

错误：

| Sno  | 电话        |
| ---- | ----------- |
| 1    | 123,456,789 |

如果“电话”这一列同时放三个电话号码，就不满足原子性。

更合理的是拆开设计。

考试记：

> **1NF：每个属性都是不可再分的基本数据项。**

------

## 第二范式 2NF

前提：

> 必须先满足 1NF。

核心：

> **所有非主属性都必须完全函数依赖于候选键，不能存在部分函数依赖。**

例如主键：

(Sno,Cno)

存在：

Sno→Sname

于是：

(Sno,Cno)→Sname

是部分函数依赖。

因此不满足 2NF。

解决方法就是拆表：

```
学生表：
Sno, Sname


选课表：
Sno, Cno, Grade
```

记：

> **2NF 消除非主属性对候选键的部分依赖。**

------

## 第三范式 3NF

前提：

> 已经满足 2NF。

核心：

> **非主属性不能传递依赖于候选键。**

例如：

Sno→SdeptSdept→Mname

所以：

Sno→Mname

Mname 是通过 Sdept 间接依赖 Sno 的。

因此存在传递依赖。

解决方案：

```
学生表：
Sno, Sname, Sdept


学院表：
Sdept, Mname
```

记：

> **3NF 消除非主属性对候选键的传递依赖。**

------

## BCNF

BCNF 是比 3NF 更严格的一种范式。

最标准的定义是：

对于关系中的每一个非平凡函数依赖：

X→Y

要求：

> **X 必须是超键。**

也就是说：

> **只要某个属性能够决定其他属性，那么这个“决定者”必须具有候选键级别的唯一确定能力。**

截图里可以概括为：

> 在 3NF 基础上，进一步消除“非候选键属性决定其他属性”的情况。

注意一点：截图中“BCNF 是 3NF 的子集”的表达从集合关系角度容易造成理解混乱，更准确地说是：

> **满足 BCNF 的关系一定满足 3NF，但满足 3NF 的关系不一定满足 BCNF。**

所以要求严格程度：

1NF<2NF<3NF<BCNF

------

## 四种范式怎么记

这是最值得背的一组：

| 范式     | 核心要求                 | 主要解决             |
| -------- | ------------------------ | -------------------- |
| **1NF**  | 属性不可再分             | 单元格存多个值       |
| **2NF**  | 非主属性完全依赖候选键   | 部分依赖             |
| **3NF**  | 非主属性不传递依赖候选键 | 传递依赖             |
| **BCNF** | 每个决定因素都必须是超键 | 更复杂的函数依赖问题 |

可以直接背一句：

> **1NF 要原子，2NF 去部分，3NF 去传递，BCNF 要求决定因素都是键。**
